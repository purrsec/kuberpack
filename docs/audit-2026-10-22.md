# Audit Kuberpack — 22 octobre 2026

Ce rapport conserve l'état de l'audit initial, avant la refonte de
`kuberpack install`. Les corrections d'installation et leurs vérifications
ultérieures sont suivies dans [la validation Docker](install-validation-2026-10-22.md)
puis [l'essai sur VPS vierge](install-vps-2026-10-22.md).

## Verdict et périmètre

La base compile et ses tests passent, mais l'état repris de DSH ne respectait
pas encore le parcours annoncé. Le démarrage des pods ne suffisait pas à
valider l'installation, la compilation d'un projet ou la gestion des secrets.

Cet audit porte sur le CLI, le compilateur de projets, les chemins GitOps,
l'inventaire opérationnel, les secrets et le déploiement d'une image tierce.
Il utilise le compte GitHub de test `user345679` et le VPS k3s existant.
Il ne constitue pas une validation d'une installation sur un cluster vide,
ni une certification des providers GitLab, Forgejo ou des registres privés.

## Contrat développeur retenu

1. Le développeur prépare ses secrets dans Infisical avec son CLI.
2. Il écrit un seul `kuberpack.yaml`, à la main ou avec `project init`.
3. Il relit ce fichier, puis lance `kuberpack project compile`.
4. Le control plane génère et pousse le GitOps ; Flux applique les ressources.
5. Les futurs changements passent par ce manifeste ou les pushes de code.

Le développeur n'écrit pas de HelmRelease, de NetworkPolicy, de PVC ni de
ressource Infisical. Le fichier ne contient que des noms de secrets.

## Défauts corrigés pendant l'audit

| Défaut observé | Correction |
| --- | --- |
| `project init` appelait `create` et déployait immédiatement, sans créer le fichier local annoncé. | `init` écrit un fichier local, fonctionne sans API et refuse d'écraser un fichier existant. `compile` envoie ensuite ce fichier sans le réécrire. |
| Les services utilisant `image:` n'apparaissaient pas dans l'inventaire des applications. | Inventaire SQLite des services publiés, reconstruit depuis le manifeste, exposé par l'API et le CLI. Aucun build ni webhook fictif. |
| Les secrets étaient optionnels et `envFrom` pouvait injecter des clés non déclarées. | Chaque clé déclarée est injectée par un `secretKeyRef` obligatoire. Retirer une clé du manifeste la retire du pod généré. |
| Déclarer des secrets sans configurer Infisical était silencieusement accepté. | Échec explicite à la compilation. |
| La synchronisation des secrets dépendait d'un dossier extérieur aux projets et de la configuration de la racine GitOps. Une copie locale était générée mais jamais référencée. | La ressource de synchronisation appartient désormais au projet, référence l'authentification de la plateforme et est appliquée avec lui. |
| La migration du dernier ancien secret laissait une référence vers une kustomization vide. Défaut constaté lors du premier déploiement de cet audit. | Suppression de la référence vide dans le même commit ; test de migration qui reconstruit la racine avec Kustomize. |
| La déclaration de dix minutes de démarrage restait soumise à un timeout Helm de deux minutes et à un test HTTP au budget plus court. | Le timeout Helm et le test HTTP suivent `startup_budget`. Les tests sont désactivés pour un service à zéro réplique. |
| Chaque commit GitOps créait une nouvelle révision de chart et redéployait toutes les applications. | `ChartVersion` pour les releases générées ; les changements du chart passent par une nouvelle version du chart. |
| Plusieurs valeurs invalides étaient acceptées jusqu'au rejet par Kubernetes. | Validation des identifiants, sources exclusives, quantités de ressources, ports, répliques, volumes et budgets ; refus des documents YAML supplémentaires. |
| L'API pouvait utiliser un nom de projet différent de celui inscrit dans le manifeste. | Refus de la divergence. |
| Le contrôle de capacité globale était contourné par la compilation via l'API. | Le même contrôle est exécuté après lecture du dépôt dans ce parcours. |
| L'admission additionnait les limites CPU maximales ; le VPS refusait Stirling alors que les réservations tenaient. Les ressources par défaut étaient aussi omises du calcul. | Admission sur les demandes CPU, mémoire contrôlée sur les limites, prise en compte des valeurs par défaut du chart. |
| Une image sans tag pouvait produire une référence invalide ; les images officielles Docker sans namespace étaient mal résolues. | Défaut `latest`, namespace `library/` et correction du chemin API Quay. |
| Le builder tentait de supprimer un Job échoué sans disposer de ce droit. | Ajout du verbe `delete` sur les Jobs du namespace de build. |
| Les images publiques référençaient un Secret de pull inexistant, ce qui produit un avertissement sur le pod Stirling. | Elles n'héritent plus des identifiants du registre de build ni de ses droits RBAC. |
| Le chart utilisait un rolling update pour les applications ayant des disques, autorisant deux processus à ouvrir le même fichier de base. | Stratégie `Recreate` quand le service utilise un volume persistant ; aucune modification du manifeste développeur. |
| La migration d'une Deployment existante vers `Recreate` a échoué avec le server-side apply de Helm 4, puis a été rollbackée. | Pour les services avec disque, l'upgrade et le rollback utilisent le remplacement par application côté client, qui retire les anciens paramètres RollingUpdate. Contrat Flux 2.8 ou plus. |
| Pendant la reprise, Helm pouvait annoncer un test réussi alors que le nouveau pod n'était pas prêt : le hook HTTP avait atteint l'ancien pod. | Attente de la nouvelle révision avant le test HTTP. Le timeout suit le budget de démarrage et Flux 2.8+ peut interrompre l'attente quand une correction arrive. |
| Le rebuild réel de Comptoir a été expulsé par Kubernetes : le cache de build dépassait sa limite de 1050 Mo. Le calcul préalable ignorait ce cache, et l'API ne renvoyait que `job: failed`. | Plancher de 2 Gio pour les couches actives, inclusion du cache dans le contrôle de disque libre, restitution du motif d'éviction depuis le statut du pod, même si Kubernetes a déjà supprimé ses logs. |

## État de la plateforme de test

La VM dispose de quatre CPU et d'environ 12 Go de mémoire. La configuration
Kuberpack conservait `3916Mi` et trois CPU après l'agrandissement de la VM.
Le GitOps de la **plateforme** a été mis à jour avec sa capacité allocatable.
Cette configuration d'exploitation n'est pas une demande au développeur
d'écrire des ressources Kubernetes pour son application.

Les anciennes démos `demo`, `ntfy`, `secretdemo` et `vault` ont été mises à
zéro réplique **via leurs manifestes et le CLI Kuberpack**, pour libérer le
budget mémoire nécessaire à Stirling. Les volumes et les bases n'ont pas été
supprimés. Le builder a reçu une limite de 3 Gio sur la VM agrandie.

Le premier déploiement des corrections a rencontré le défaut de migration
du dossier de secrets vide. La racine de la plateforme a dû être réparée
pour permettre le déploiement de la correction. Cette intervention est
consignée : elle ne doit pas être présentée comme une migration initialement
réussie sans intervention.

Le test du CLI Infisical avec un **compte humain** a d'abord reçu un `403` :
le projet préparé par DSH ne contenait que ses identités machine. Le compte
administrateur local existant a été rattaché au projet avec le rôle membre,
par l'API d'administration. Cet onboarding d'exploitation reste à automatiser
ou à rendre explicite ; il ne fait pas partie des ressources de l'application.

## Points ouverts qui empêchent de qualifier le produit de terminé

| Priorité | Constat dans le code ou le cluster |
| --- | --- |
| P1 | `install` prépare des dépendances et des secrets, mais demande encore d'installer Flux et de déployer le control plane avec Helm. La promesse d'une installation complète en une commande n'est pas tenue. |
| P1 | Le code d'installation Infisical crée les ressources Kubernetes, mais ne configure pas lui-même, par l'API Infisical, la méthode Kubernetes de l'identité, le projet de secrets et ses accès humains. Le VPS repris de DSH bénéficie d'opérations manuelles préalables. La seule installation des charts ne reproduit pas ce raccordement. |
| P1 | Les mots de passe PostgreSQL et Redis d'Infisical sont codés en dur dans les valeurs du chart. Le Secret de bootstrap est aussi réécrit avec un nouveau mot de passe lors d'une réinstallation, sans rotation du compte déjà créé. |
| P1 | Le parcours d'installation peut remplacer des jetons existants et générer un nouveau jeton d'API à chaque exécution. Il faut un contrat explicite de conservation et de rotation avant de parler d'idempotence complète. |
| P1 | Le Secret de pull d'une application construite est produit avec le jeton de lecture du code. Des jetons réellement séparés peuvent donc casser le pull d'une image privée. Le compte de test réutilisait le même PAT. |
| P1 | Le control plane écrit directement les ConfigMaps de valeurs et demande des réconciliations Helm. Ce comportement diverge de l'architecture documentée où le déploiement de production passe uniquement par Git et Flux. |
| P1 | Les erreurs de pose du webhook, de lecture de branche et de synchronisation des valeurs sont parfois seulement journalisées, alors que l'API peut annoncer une compilation réussie. |
| P1 | L'historique de Comptoir conserve plusieurs anciens builds `running` alors qu'aucun Job correspondant ne tourne. La reprise de l'état opérationnel après redémarrage doit être fiabilisée. |
| P1 | Le VPS contient deux Kustomizations Flux (`projects` et `kuberpack-projects`) avec `prune: true`, appliquant toutes deux `./kubernetes/vps/projects`. L'installateur ne réutilise pas automatiquement une configuration équivalente déjà présente sous un autre nom. |
| P2 | La contrainte d'unicité d'un dépôt dans l'inventaire des builds empêche plusieurs services d'un monorepo de partager ce dépôt. Les services publiés n'ont plus cette contrainte. |
| P2 | La capacité reste une configuration de plateforme ; l'agrandissement d'une VM n'est pas détecté automatiquement. |
| P2 | Les projets déjà générés bénéficient d'une exemption au contrôle de capacité globale. Une augmentation de leurs ressources nécessite un contrat d'admission plus précis. |
| P2 | `compile --dry-run` valide le manifeste local et l'affiche ; il ne produit pas un plan distant complet ni un diff de toutes les ressources générées. |
| P2 | Le CLI n'expose pas encore un parcours complet d'attente et de diagnostic du runtime pour une image publiée. `apps` montre l'application, mais ne prouve pas sa santé. |

## Vérifications

- `make test` : analyse `go vet` et suite Go complète.
- `go test -race ./internal/builder ./internal/control ./internal/store` : builder, inventaire et état opérationnel.
- Tests ajoutés : `init` local puis `compile`, entrées invalides, secrets
  obligatoires et mise à jour des clés, génération Kustomize autonome,
  migration du dernier ancien secret, délais cohérents, inventaire des images.
- Le manifeste de référence Stirling est dans
  [`examples/stirling-pdf/kuberpack.yaml`](../examples/stirling-pdf/kuberpack.yaml).
